# The Imperivm I and II campaigns, built in

Goal: a player of Imperivm Resurrected finds the campaigns of Imperivm I (La guerra de las Galias) and Imperivm II (Hannibal's
Campaigns, The Punic Wars, Numantia) working in Great Battles, without Node, without the old games installed and without copying
folders by hand.

The maintainer has the rights holder's permission to distribute them. They are still not GPL code: the converted files never enter
this repository, and they ship as their own packs with their own notice.

## What there is today

- `tools/imperivm1/convert.js` (in `main`) and `tools/imperivm2/convert.js` (only on `fix/imperivm1-reduce-group`, with the
  Imperivm II combat in `src/game/i1engine.cpp`: 3 commits not in `main`) convert the campaigns from local installs of the old games.
- The output is six mods: `imperivm1-campaign` + `imperivm1-campaign-data`, and `imperivm2-data` + `imperivm2-hannibals-campaigns`,
  `imperivm2-the-punic-wars`, `imperivm2-numantia`. They take about 440 MB on disk: 242 MB the Imperivm I adventure, 83 MB The Punic
  Wars, 79 MB Imperivm II's movies. Their `mod.json` says `"redistributable": false`.
- Great Battles already finds them (`BattleCampaignPackOf` in `src/game/battlelist.cpp`). When none is installed or active, the
  Imperivm I and II cards say "Disabled / Turn it on in Additional content" (`src/ui/battlesui*.cpp`).
- `src/mods/downloads.cpp` already downloads and unpacks an archive from a URL with its size and SHA-256 (`DlInstallEntry`,
  `DownloadFile`), with progress in `DlStatus()`.

## Decisions

### 1. Where the packs live: GameBanana, one page per game

At 440 MB the packs cannot travel in the mod's zip: every update of the mod would download them again.

- **GameBanana, two pages published by the maintainer**: "Imperivm I - La guerra de las Galias" and "Imperivm II - Campaigns", each
  with its notice in the description and a `NOTICE.txt` in the zip ("© FX Interactive / Dinamic Software, distributed with
  permission; not covered by the GPL").
  - The mod already downloads from GameBanana, picking the fastest of its file servers (`src/mods/serverpick.cpp`, `gbdownload.cpp`),
    and installs, checks and updates what it downloads there.
  - Players already look for content there and in the mod's catalog.
  - The code repository stays free of game files.
- The DLL pins an exact GameBanana file (id, size and MD5, as the catalog gives them), not "the latest". A newer file on the page
  does not reach players until a DLL whose classes match it.
- If GameBanana refuses a file (size or rules), the fallback is a GitHub release of a separate repository, `THIONG/imperivm-campaigns`
  (2 GB per file). Only the URL in the table changes.

### 2. The DLL pins the packs it needs

The data mods and `i1engine.cpp` must match: a new converter changes the classes the DLL fights with. So each DLL carries the
exact packs it works with, in a generated table:

```text
src/mods/campaignpacks_data.cpp   (generated by tools/build-campaign-packs.js, committed with its source like tr_data.cpp)
  { "imperivm1", version, gbId, gbFileId, md5, bytes, { "imperivm1-campaign", "imperivm1-campaign-data" } }
  { "imperivm2", version, gbId, gbFileId, md5, bytes, { "imperivm2-data", "imperivm2-hannibals-campaigns", ... } }
```

`tools/build-campaign-packs.js` (maintainer only, needs the old games installed) runs both converters, writes the mods with
`"redistributable": true`, `"authors": ["Imperivm Resurrected"]` and a `NOTICE.txt`, packs one zip per game, and prints the table.
The maintainer uploads the zips to the two GameBanana pages and runs the tool again with the file ids to fill the table. A new DLL with new packs is a normal mod release. One without changes keeps the table.

### 3. Getting them: one click on the card, and optionally in the installer

The Imperivm I and II cards of Great Battles replace "Disabled" with the pack's state:

| State | Card |
|---|---|
| Not downloaded | "Download the campaign · 181 MB" (Imperivm I) or "· 160 MB" (Imperivm II), from the table |
| Downloading | The same download as in "Browse content" (`DlInstallEntry`), with its progress bar, speed and unpacking step from `DlStatus()`, drawn on the card; it can be cancelled and keeps going if the player leaves the screen |
| Downloaded, older than the DLL's table | "Update the campaign · N MB" |
| Downloaded, not active | "Play" turns it on (see 4) |
| Active | As now: the campaign's adventures |

The covers are the mod's own, not the packs': `mod/campaigns/` (shipped in the release zip like `mod/brand/`) holds one picture per
campaign card and per adventure. The cards show them before anything is downloaded, so Imperivm I and II look like part of the
game from the first launch. They must be new art made for Imperivm Resurrected, never a picture taken from the old games, because they live in this
repository. They get the license of the mod's other images. Until they exist, a card shows the laurel before the download and the
pack's own picture after it. A cover can be replaced in a later release without touching the packs.

The installer gets an optional box, "Imperivm I and II campaigns (≈ 440 MB)", which downloads the same zips. A clean install
then has them from the first launch.

### 4. The adventures are always there; their data turns on when a campaign is played

The `-data` mods add classes (`I1*`, `I2*`), AI profiles, two command files (`imperivm1.xml`, `imperivm2.xml`) and patches that add
the new classes as sources of existing commands (`hero.xml`, `unit.xml`...). They live in `data/`, so turning them on restarts the game.

They cannot be always on and left out of the room's fingerprint. Checked in `gbr.exe`:

- `CCmdRegistry::GetCommandsChecksum` (`004f5f40`) is a hash of the command names that the peers compare, so an extra
  `imperivm1.xml` changes it.
- `CCmdRegistry::SerializeCommand` (`004f5f60`) sends a command as its index in the registry (ushort, `CCmdDesc+0x1e4`, given in
  load order by `004ed2b0`). Commands loaded from an extra file shift the indices of the files after it.

So:

- The **adventure mods** (maps only) of the official packs are mounted with every profile, Original included. They do not touch
  gameplay and load without a restart, so the cards and the adventures are always there.
- The **data mods** are mounted only when needed. "Play" or "Continue" on an Imperivm I/II adventure without its data mod mounted says
  "The game restarts to load Imperivm I's units", adds the data mod to the active profile and restarts once. Later campaign games
  start directly.
- Online nothing new is needed. A room whose content differs already restarts the game with the room's content
  (`RoomContent::kOtherGameplay`), and that leaves the data mods out.

### 5. Hot loading

As now: each adventure stays in a mod of maps only, and its data in the `-data` mod, so a new adventure loads without restarting.

## Order of work

1. Bring the 3 commits of `fix/imperivm1-reduce-group` into this branch (the Imperivm II converter and combat). Or merge that
   branch to `main` first in its own PR.
2. Mark the official packs (`"official": "imperivm1"` in `mod.json`) and mount their adventure mods with every profile.
3. `tools/build-campaign-packs.js` and the generated `campaignpacks_data.cpp`, with a test that the table parses and every pack
   names its mods.
4. Download, update and activation of a pack (`src/mods/campaignpacks.cpp`), on top of `downloads.cpp`.
5. The Imperivm I and II cards (`src/ui/battlesui*`), with es/it texts.
6. The installer option.
7. The restart that turns on a campaign's data mod from "Play" and "Continue".
8. Tried in the game: download from the card on a profile without them, play both campaigns, join an online room with and without them.
